## Problem Statement

The analysis output feels generic across different repos:

- **Mermaid diagrams** in Overview and Architecture are built from keyword heuristics (`charts.ts`), not from AI understanding of the actual codebase. They classify modules by checking if names contain words like "page", "component", or "database" and slot them into fixed subgraph templates.
- **Codemap** renders a hardcoded 6-section layout (`CodemapSection.tsx:buildCodemapSections`) from `brief.entrypoints`, `brief.architecture.keyModules`, and `brief.architecture.apis`. It completely ignores the AI-generated `brief.codemap` data that the synthesis model produces with citations and hierarchical structure.
- **Exploration depth** is limited by an 80 API call budget, 20 iteration cap, 500-line file read truncation, and 8KB per-result cap fed back to the conversation — meaning the agent sees a fraction of most codebases.

## Implementation Phases

### Phase 1: Render the AI Codemap

**Goal:** Use the rich, citation-backed codemap the synthesis model already generates instead of the hardcoded layout.

**Priority:** Highest — this is unused work that's already being produced.

#### Changes

**`src/components/sections/CodemapSection.tsx`**

1. Check if `brief.codemap` exists and has nodes with content.
2. If yes, render the AI codemap with its hierarchical nodes, descriptions, and citation links.
3. If no (fallback for static analysis briefs), keep the current `buildCodemapSections()` output.
4. Preserve the existing CodeViewer integration — citations in the AI codemap should open the code viewer the same way.

```
Pseudocode:

function CodemapSection({ brief }) {
  // Prefer AI-generated codemap when available
  if (brief.codemap?.nodes?.length > 0) {
    return <AICodemapView codemap={brief.codemap} repoInfo={brief.repoInfo} />
  }
  // Fallback to static layout
  return <StaticCodemapView brief={brief} />
}

// AICodemapView renders codemap.nodes recursively:
// - Each node: title, markdown description, expand/collapse children
// - Citations render as clickable code refs that open CodeViewer
// - codemap.summary shown as header text
```

#### Key details
- The AI codemap nodes have: `id`, `title`, `description`, `children[]`, `citations[]`
- Each citation has: `id`, `filePath`, `startLine`, `endLine`, `snippet`
- The `description` field contains markdown with `[[file:path/to/file.ts:42]]` references
- Parse these inline references and make them clickable (same as citation links)
- Keep the split-pane layout (doc left, CodeViewer right)

#### Acceptance criteria
- AI codemap renders when `brief.codemap` has nodes
- Citations open the CodeViewer to the correct file and line
- Fallback still works for briefs without codemap data
- Nodes are collapsible with expand/collapse

### Phase 2: AI-Generated Mermaid Diagrams

**Goal:** Replace the keyword-heuristic diagrams with diagrams generated by the synthesis model, which actually understands the codebase.

**Priority:** High — the current diagrams are the most visibly "generic" part of the output.

#### Changes

**`src/lib/agent/prompts.ts` — Update `SYNTHESIS_PROMPT`**

Add a `diagrams` field to the JSON schema:

```json
"diagrams": {
  "overview": "A mermaid graph TD showing the actual high-level data flow: user → frontend → API → services → data stores → external services. Use real module/component names from the codebase, not generic labels. Show the actual request lifecycle.",
  "architecture": "A mermaid graph TD showing how the key modules relate to each other. Show actual import/dependency relationships you observed, not just layer groupings.",
  "stack": "A mermaid graph TD showing the technology stack layers with the actual technologies used."
}
```

Add instructions in the prompt:

```
### Diagram Rules
- Use actual module names, component names, and service names from the code
- Show real relationships you observed (imports, API calls, data flow), not assumptions
- Keep diagrams focused: 8-15 nodes max, prefer clarity over completeness
- Use subgraphs to group related nodes logically
- Sanitize node labels: no special characters (){}[]|;#& — use only alphanumeric, spaces, hyphens
- Wrap all node labels in double quotes inside brackets: N1["Label Here"]
- Valid mermaid syntax only — test mentally before outputting
```

**`src/lib/types.ts` — Add diagram fields**

```typescript
// In the ProjectBrief or a nested type:
diagrams?: {
  overview?: string;    // mermaid chart string
  architecture?: string;
  stack?: string;
}
```

**`src/lib/agent/orchestrator.ts` — Parse diagrams from synthesis**

In `buildBriefFromSynthesis`, extract `data.diagrams` and attach to the brief.

**`src/components/sections/OverviewSection.tsx`**

```
// Before:
const flowChart = buildOverviewFlowChart(brief);

// After:
const flowChart = brief.diagrams?.overview || buildOverviewFlowChart(brief);
```

**`src/components/sections/ArchitectureSection.tsx`**

```
// Before:
const systemChart = buildArchitectureChart(brief);
const stackChart = buildStackLayersChart(brief);

// After:
const systemChart = brief.diagrams?.architecture || buildArchitectureChart(brief);
const stackChart = brief.diagrams?.stack || buildStackLayersChart(brief);
```

**`src/lib/charts.ts`** — No changes needed. Keep as fallback for static analysis briefs.

#### Mermaid validation
- The synthesis model may produce invalid mermaid syntax. The `MermaidChart` component should already handle render failures gracefully (show nothing or show a fallback). Verify this.
- If it doesn't, add a try/catch in MermaidChart that falls back to the heuristic chart on render error.

#### Acceptance criteria
- Synthesis prompt requests mermaid diagrams
- AI diagrams render in Overview and Architecture when present
- Heuristic charts used as fallback when AI diagrams are missing or invalid
- Diagrams use real names from the analyzed codebase

### Phase 3: Richer Synthesis Context

**Goal:** Give the synthesis model more concrete data to work with so its output is specific and evidence-based.

**Priority:** High — this directly improves the quality of everything the synthesis model produces (codemap, diagrams, features, architecture).

#### Changes

**`src/lib/agent/orchestrator.ts` — `synthesize()` function**

Currently (lines 261-283) only passes `explorationSummary` (concatenated assistant texts) and a list of read file paths. Enhance to also include:

1. **Key file contents** — include the actual content of the most important files read during exploration (entry points, configs, main modules). Budget ~30KB of raw file content.

```typescript
// Collect the most informative file reads
const keyReads = toolResults
  .filter(r => (r.tool === "readFile" || r.tool === "readFileLines") && !r.error)
  .sort((a, b) => {
    // Prioritize: entry points > configs > source files
    const priority = (path: string) => {
      if (path.includes("package.json") || path.includes("tsconfig")) return 0;
      if (path.match(/app\/.*page\.(tsx?|jsx?)$/)) return 1;
      if (path.match(/app\/.*layout\.(tsx?|jsx?)$/)) return 1;
      if (path.match(/api\/.*route\.(tsx?|jsx?)$/)) return 2;
      if (path.includes("/lib/") || path.includes("/utils/")) return 3;
      return 4;
    };
    return priority(a.params.path as string) - priority(b.params.path as string);
  });

// Include top files within a size budget
let budget = 30_000;
const includedFiles: string[] = [];
for (const r of keyReads) {
  const content = r.result;
  if (content.length <= budget) {
    includedFiles.push(`### ${r.params.path}\n\`\`\`\n${content}\n\`\`\``);
    budget -= content.length;
  }
  if (budget <= 0) break;
}
```

2. **Search results summary** — include what patterns were searched and where they were found.

3. Pass this as a separate section in the synthesis user message:
```
## Key File Contents
${includedFiles.join("\n\n")}

## Search Findings
${searchSummary}
```

#### Acceptance criteria
- Synthesis model receives actual file contents for key files
- Output references real function names, variable names, and patterns
- Total synthesis input stays under model context limits (~100K tokens for Gemini Pro)

### Phase 5: Structured Exploration Strategy

**Goal:** Make the exploration agent produce better raw findings by guiding it to map relationships, not just read files.

**Priority:** Medium — improves the quality of raw data before synthesis.

#### Changes

**`src/lib/agent/prompts.ts` — `buildExplorationPrompt()`**

Add to the "Your Task" section:

```
### What to Track
As you explore, build and maintain a mental model of:

1. **Import/dependency graph**: Which modules import which? What are the key hub files that everything depends on?
2. **Request lifecycle**: Trace at least one complete flow: user action → component → API call → service logic → database/external service → response rendering
3. **State management**: How is application state managed? What are the stores/contexts and what do they hold?
4. **Data models**: What are the core entities/types? Where are they defined and how do they flow through the system?
5. **Configuration & environment**: What env vars, feature flags, or config files control behavior?

### Output Format
When you finish exploring, structure your findings as:

1. **Architecture Overview** — framework, patterns, key abstractions
2. **Module Map** — each major module with its purpose and key exports
3. **Data Flow** — how data moves through the system (request lifecycle)
4. **Dependency Graph** — which modules depend on which (actual imports you saw)
5. **Key Patterns** — auth, error handling, validation, caching, etc.
6. **Notable Details** — anything surprising, complex, or particularly well/poorly designed
```

#### Acceptance criteria
- Exploration agent produces structured findings with relationship data
- Synthesis model receives dependency graph and data flow information
- Output diagrams reflect actual observed relationships

## Testing Strategy

### Manual testing
- Analyze 3-5 diverse repos (small/medium/large, different frameworks)
- Compare before/after for each section: Overview diagram, Architecture diagrams, Codemap
- Verify codemap citations link to correct files and lines
- Test fallback paths: static analysis brief, missing codemap, invalid mermaid syntax

### What to check per phase
- **Phase 1:** Codemap renders AI nodes when available; static fallback works; CodeViewer opens correctly
- **Phase 2:** Diagrams show real module names; invalid mermaid falls back gracefully; no blank diagram sections
- **Phase 3:** Synthesis output references real function/class names; descriptions are specific not generic
- **Phase 4:** No timeout on large repos; analysis covers more files; cost increase is acceptable
- **Phase 5:** Exploration output is structured; dependency info appears in final brief

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| AI mermaid syntax is invalid | Blank diagrams | Fallback to heuristic charts; validate in MermaidChart component |
| Larger context → slower/more expensive | Higher cost per analysis | Budget caps still enforced; configurable per plan tier |
| Synthesis model overwhelmed by too much raw content | Lower quality output | Cap raw file content at 30KB; prioritize key files |
| Exploration takes too long with higher iteration count | Timeouts | Increase maxDuration; keep abort controller timeouts |
| AI codemap has empty or low-quality nodes | Worse than static layout | Only render AI codemap if nodes have meaningful content; fallback otherwise |
